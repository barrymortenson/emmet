# ADR 0002: App E2E with WebdriverIO and the embedded WebDriver server

Status: accepted, 2026-10-24 (session 0B).

## Context

Section 16's app E2E layer drives the real Tauri app on both OSes. The plan named `@wdio/tauri-service` with the
embedded `tauri-plugin-wdio-webdriver` (debug builds only), because WKWebView has no WebDriver of its own; if macOS
failed, the fallback was Playwright on WebKit against Vite with a mocked IPC on macOS, and wdio on Windows.

## Decision

The plan's choice works on both OSes, so no fallback is needed.

- **Packages** (all MIT): `@wdio/tauri-service` 1.5.1, which needs WebdriverIO 9 (`peerDependencies: webdriverio
  ^9.0.0`), so the runner is `@wdio/cli`, `@wdio/local-runner`, `@wdio/mocha-framework`, and `@wdio/spec-reporter`
  9.32.0 with `@wdio/globals` 9.31.3, in `tests/e2e/` (a pnpm workspace package); and the crate
  `tauri-plugin-wdio-webdriver` 1.5.1 (https://github.com/webdriverio/desktop-mobile, MIT). The project's own ADR
  (`docs/adr/0002-tauri-embedded-webdriver-default.md` there) explains the embedded server: an in-app W3C WebDriver
  server on WKWebView, WebView2, and WebKitGTK, with no external driver and no subscription.
- **Never in a release build.** The plugin is an optional dependency behind `emmet-desktop`'s `webdriver` feature,
  which only `just e2e` turns on (`pnpm tauri build --debug --no-bundle --features webdriver`), and `main.rs` has
  `compile_error!` for the feature without `debug_assertions`. (A `cfg(debug_assertions)` target dependency, as the
  plugin's README suggests, doesn't keep a crate out of a release build, since Cargo evaluates target cfgs without the
  profile.) The plugin's README asks for `wdio-webdriver:default` in the capabilities; its default permission set is
  empty, so it isn't added: **the capabilities and CSP are unchanged.**
- **The service's focus check.** Before each `findElement`, `$`, `elementClick`, or `getTitle`, the service asks the
  app for its window states through `plugin:wdio|get_window_states`, a command of the service's other plugin
  (`tauri-plugin-wdio`), and waits 5 s for `window.__TAURI__` when it isn't there. Emmet doesn't use that plugin (it
  needs a frontend package and a capability). `wdio.conf.mjs` calls `browser.tauri.switchWindow("main")` in
  `beforeSuite`, which marks the window as chosen and turns the check off; with one window that's correct. Cost: one
  5 s wait at the start of a run.
- **No browser driver downloads.** `pnpm-workspace.yaml`'s `allowBuilds` keeps `edgedriver` and `geckodriver`'s
  install scripts (and esbuild's check script) from running.
- **The 0A window** gets one button for the hello-world to click; 1B and 2B replace the window.

## Evidence

- `tests/e2e/specs/hello.e2e.mjs`: the app shows "Emmet" and "Version …", there's no greeting, a click on `#hello`
  shows "Hello from Emmet".
- macOS, on this Mac: `just e2e` → `Spec Files: 1 passed, 1 total (100% completed) in 00:00:05`. By hand, the
  embedded server answers raw W3C requests: `GET /status` → `tauri-plugin-webdriver is ready`; a new session reports
  `browserName: webkit`, `platformName: macos`; the title is "Emmet" and `h1` resolves.
- CI, PR #3: CI_RESULT

## Consequences

- `just e2e` runs in `just ci` (the mac job) and in the windows job. The full debug build with the plugin adds
  WINDOWS_TIME to the windows job; section 16's budget (≤ 15 minutes) holds.
- 1B extends the harness (first run, slider, viewer stats) on this setup.

## Rerun

```sh
just e2e          # builds the debug app with the webdriver feature and runs every spec
just e2e hello    # one spec

# The embedded server by hand
TAURI_WEBDRIVER_PORT=4455 target/debug/emmet-desktop &
curl -s http://127.0.0.1:4455/status
curl -s -X POST http://127.0.0.1:4455/session -H 'content-type: application/json' -d '{"capabilities":{}}'
```
