## Design notes

- **Crate layout.** `emmet-agent`: `lib.rs` (the section 10 types and traits), `session.rs` (the shared engine),
  `hub.rs` (what `emmet_host` and `emmet mcp --session` reach over the bus: approvals, questions, pending notes),
  `claude.rs`, `codex.rs` (+ `codex/types.rs`, checked against the committed schema), `detect.rs`, `env.rs` (the
  login-shell environment), `usage.rs`, `keychain.rs`, `transcript.rs`. The bus stays generic: `Approve`, `Ask`, and
  `Notes` messages carry JSON; the app and the test harness pass them to the hub.
- **The engine.** A session is a child process plus a `Protocol` (one per CLI): `start`, `send`, `steer`,
  `interrupt`, `respond`, `on_message`. The engine owns stdin, a reader thread, the transcript
  (`.emmet/transcripts/<session>.jsonl`, the same `{t, dir, msg}` lines as 0B, so a scrubbed live session is a replay
  fixture), turn state, file-change detection (a snapshot of the project's sources after each tool result), and exit
  handling (an exit mid-turn is `Error{Crashed}` + `TurnDone{Crashed}` with the last stderr lines).
- **Redirects (D-33).** A note waits in the engine, editable and cancelable, until the agent's next step: when a tool
  call is in progress (or the next one starts), it goes out natively (Claude: a stream-JSON user message; Codex:
  `turn/steer`). If the native path is off or refused, the note waits in the hub and `emmet mcp --session` attaches it
  to the next Emmet tool result as `user_notes`. If the turn ends first, the notes go out as the next turn; after Stop,
  prefixed "(You stopped the previous turn.)".
- **Approvals.** Claude: `emmet mcp-host approve` allows reads and edits inside the project (paths canonicalized,
  links out refused), remembers "Allow for this session", and sends everything else to the app as a card over the bus;
  with no app it denies with a reason. Codex: server requests become cards; Emmet accepts the `mcp_tool_call`
  elicitations for its own two servers and declines other servers' (8F adds the per-tool ask).
- **Questions (D-32).** `emmet mcp-host ask_user` holds a bus request until the user answers, Stop cancels it
  (`reason: "stopped"`), or it nears the tool timeout (`reason: "timeout"`).
- **Doctrine.** `crates/emmet-cli/doctrine/EMMET.md` (printed by `emmet rules`, and by the new MCP `rules` tool) and
  `doctrine/api.md` (printed by `emmet api` and the MCP `api` tool), generated from emmet_dsl's docstrings by
  `python -m emmet_dsl.api`, with a freshness test. The pointer goes through `--append-system-prompt` and
  `developerInstructions`, and into new projects' AGENTS.md. Section 10 says the doctrine "is read once through a
  tool", and section 09 had no such tool, so `rules` and `api` join the MCP table.
- **Plans and keys (D-35, D-37).** Claude runs with the login shell's environment (`$SHELL -ilc` on macOS, read once
  per launch; the app's own on Windows) plus `MCP_TOOL_TIMEOUT` only. Codex gets `OPENAI_API_KEY` from the keychain
  through the provider block. The badge: `system/init` `apiKeySource` ("none" is the plan, named with
  `auth status`'s `subscriptionType`), and "Codex · API key".
- **Usage (D-36).** `usage()` for Claude sends `/usage` to a short-lived `claude -p` in an empty app-data folder with
  no MCP servers and `--no-session-persistence`; the host fetches it only when the user opens the popover, presses ⟳,
  or finishes a turn, at most once a minute. `rate_limit_event` updates it between fetches. Codex reports its billing
  state only.
- **Test seams.** The fake agents are picked with `EMMET_CLAUDE_BIN` and `EMMET_CODEX_BIN`, and read their scenario
  from `EMMET_FAKE_DIR`. Tests use a file keychain (`EMMET_FAKE_KEYCHAIN`), never the real one. The fakes replay a
  transcript: they wait for each `in` line, substitute paths, call the real MCP servers for tools they have (and
  `emmet_host approve` where 0B's stub logged one), apply `Edit`/`Write` and Codex `fileChange` items to the project,
  and keep the recorded results for 0B's stub tools.
