## Design notes

- **validate v0** (`crates/emmet-core/src/check/`). Reads `build/placements.json` (running the model first when
  `build/` is stale, as `emmet render` does) and writes `build/validation.json` in section 11's shape. Rules:
  - `collision` (error): body boxes (studs left out, from the parts index), shrunk 1 LDU on every side, as oriented
    boxes in world space; a pair whose shrunk boxes overlap by more than 0.5 LDU on the separating axes collides. A
    window or door frame and the glass or door inside it are exempt.
  - `floating` (error): stud connections make a graph. A stud (a primitive from the table in `check/connectors.rs`,
    with a test per primitive) connects its part to another part when it enters that part's body box through its
    bottom face. Every component with a part on the model's lowest level is grounded; any other component floats.
    The hint names the part underneath and the gap in plates.
  - `unknown_part` (error), `obsolete_part` (warning: `~Moved to` or `(Obsolete)`), `alias_part` (info, with the
    canonical id).
  - Findings are ordered by severity, then by source line, then by part id, and numbered `F-0001`…, so the same inputs
    give the same ids. Each names its parts, their `file:line` sources, a DSL-frame position, a message with numbers,
    and a hint. `[[check.allow]]` in emmet.toml (`rule`, `parts`, `reason`) moves a finding to `allowed`.
- **CLI and MCP.** `emmet check [--strict] [--rule r]` (exit 1 on errors with `--strict`); `emmet bom [--format
  json|csv]` writes `build/bom.json`. MCP `validate` (counts, the first 50 findings, the top 10 in the text with ids,
  positions, and source lines), MCP `bom`, and MCP `highlight` taking `finding: "F-0003"` as well as `ids`. `emmet
  render --highlight F-0003` highlights a finding's parts. New schemas in `docs/spec/mcp/`.
- **The app.** After each successful run the host validates and builds the BOM in-process and sends them with the
  scene. The Checks drawer lists findings (severity, message, `file:line`); a click highlights the parts as issues and
  shows the source line, read host-side from a path inside the project root. "Ask agent to fix" sends the finding to
  the current chat session (as a redirect while the agent works). The Parts drawer lists part × color × quantity. When
  the library or Python isn't set up, the app offers one Set up button (the sidecar's `library install` and `doctor
  --fix`), so the signed build works in a fresh account.
- **Build animation v0** (`packages/viewer`). `update(…, { animate: "build" })` drops added parts in one at a time, in
  build order (step, then bottom-up, then nearest to the previous part), ~30 ms apart, each falling three plates over
  160 ms with ease-out, the batch capped at 6 s. Any new update finishes it at once; renders show the final state;
  reduced motion turns it off. The app animates every run except one a slider caused, and the first scene of a
  project.
- **Doctrine.** The loop becomes run → validate → render → fix; "show a draft in the first minute"; build in visible
  stages; say numbers, including the validator's.
- **Eval v0** (`emmet eval`, `crates/emmet-cli/src/eval.rs`, dev builds; hidden from release help). Reads rung 1's
  prompt and answer script from `docs/spec/ladder.md` (embedded). Makes a temp project, starts the real CLI through
  the same adapters as the app, with the key from the keychain (`emmet-eval-anthropic`, `emmet-eval-openai`; D-37)
  and nothing else from Barry's accounts. It runs its own bus and hub, so it refuses while the app has the same data
  dir open: questions get the scripted answer, approvals allow Emmet's tools and edits to model.py and models/*.py and
  deny the rest. It prints the run count, time, and expected cost and asks before starting (D-38). Scoring per section
  16.1: runs with 0 errors; ≥ 40 parts, a door, windows, a roof; ≥ 3 params that each change the model; ≤ 10 min and
  ≤ 40 turns (a turn is a tool call or a question). Writes `docs/evals/<date>-rung1.md` and a render per run, then
  offers to save the scrubbed transcript as a replay fixture. `--dry-run` skips the keychain and the question, for
  the fake agents.
- **Signed build.** `just release-dry [--sign]`: the frontend without test hooks, `emmet` built for both Mac
  architectures and joined with `lipo`, uv at a pinned version and sha256 for both, `pnpm tauri build --target
  universal-apple-darwin` with `tauri.release.conf.json` (the sidecars and signing settings, so dev and E2E builds
  don't need them). With `--sign`: Developer ID signing with the hardened runtime, then `xcrun notarytool submit
  --keychain-profile emmet-notary --wait`, `xcrun stapler staple`, and the two checks. CI's windows path gets a job
  that builds the unsigned NSIS installer when the release files change, and weekly.
- **The replay test.** The fake agent replays a transcript where the validate result has a collision and the agent
  fixes the line; the test asserts the event sequence and a clean `emmet check` after. It starts as a derived
  transcript and is replaced by Barry's recorded live run once it exists.
