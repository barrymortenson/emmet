Emmet: build plan for an agent-driven brick CAD app

Emmet is a free desktop app for macOS and Windows that does for brick models what nurb does for CAD. You describe or change a model in plain words. Your own Claude Code or Codex agent builds it from real LDraw parts by writing a parametric Python model, and you watch it take shape in a polished 3D viewer with sliders, buildability checks, a parts list, and build steps. It's local only: no hosting, no accounts, and you bring your own agent.

Prepared 2026-10-24 · Repo barrymortenson/emmet (public, AGPL-3.0) · This plan: docs/plan.html · Status: docs/plan-status.js · Marketing site later: emmetbuilder.com

How to use this document Sections 02–18 are the specification: what to build and why. Sections 19–22 are the execution plan: nine phases, each split into a few large sessions. A session is one agent run, one branch, and one pull request. Every session has a Copy prompt with rules button that puts the agent rules, the session's scope, its Done when list, and its prompt on the clipboard in one go, ready to paste into Claude Code or Codex. Steps marked YOU need you. The left rail reads docs/plan-status.js and shows what's done, what's in progress, what's up next, and what's waiting on you.

01Read me first

Fast start

  1. Do Phase 0's people steps (section 21): approve creating the public repo (H-01, asked in 0A) and register the self-hosted runner once the repo exists (H-02). Before 0B: confirm Claude Code 2.1.310 and Codex 0.160.1 are signed in (H-03), accept Anthropic's Commercial Terms (H-20), and create the two eval API keys (H-21). The name check (H-17) is done.
  2. Open the next session. The rail's Up next box names it and has a copy button. You can also press Copy prompt with rules on the session itself.
  3. Paste it into Claude Code or Codex, started in ~/Sites/emmet. The agent checks the prerequisites, builds, tests, updates docs/plan-status.js on its branch, opens one PR, and stops.
  4. Review and merge. The status change lands with the merge, so the rail is right on the next reload. Repeat.
  5. To let one agent run a whole phase, use that phase's Copy phase prompt button (section 19). It still stops at every merge unless you add merge permission for that run.

02The product on one page

The loop

A typed request goes through the agent, which writes model.py, runs it, checks it, and fixes what the findings and render show. A slider skips the agent: Emmet writes the new value to params.json and reruns the model directly. Every run updates the viewer, and you export from there.

Who it's for

  • Brick hobbyists who already pay for Claude or Codex and want to go from an idea to a buildable, real-parts model in minutes, then tune it with sliders instead of placing 400 parts by hand. Many have never opened a terminal and are on a small plan, so Emmet installs and signs in their agent for them and helps a small plan go a long way (D-41).
  • MOC builders who want parametric drafts (a station of any length, a house of any width) and an honest parts list.

Where the chat goes past nurb

  • Question cards. When a choice is yours (style, scale, which reading of the prompt), the agent asks with a card: one question, 2–4 answers to click, and Other for your own words, like Claude Code. Its work waits until you answer (D-32, section 10).
  • Redirect without stopping. Type while the agent works, and your message reaches it at its next step, so you can correct course mid-build. Stop is still one key, and a waiting message goes out as the next turn (D-33, section 10).
  • Watch it build. New parts drop into the viewer brick by brick in build order, and the agent builds in visible stages (base, walls, roof), so you can tell early whether it's on the right track (D-34, section 13).

Gaps Emmet owns

  1. A nurb-level UI and UX in a local desktop app for brick models.
  2. Live buildability validation fed back to the agent: collisions, connectivity, floating parts, weak overhangs, part and color availability, and buildable step order.
  3. Parametric models whose sliders drive regeneration.
  4. A technique library (SNOT, hinges, jumper offsets) mined from official models, with provenance (3C).
  5. Photo to model: drop in a photo, get a parametric build from real parts (4D).
  6. Setup a non-technical person can finish. nurb and Orca expect you to install your agent and sign in from a terminal first; Emmet installs Claude Code or Codex with one click and signs in without a terminal (D-41, 1F).
  7. Native, official-style PDF building instructions (4E).
  8. Later: build from owned inventory (Rebrickable) and BrickLink pricing.

MVP scope and exit criteria

The MVP is the end of Phase 5, the working proof of concept. Beta (Phase 6) and the website and launch (Phase 7) come after it.

  • A Tauri app on macOS and Windows: 3D viewer, chat wired to Claude Code and Codex (on the user's Claude or ChatGPT plan, or an API key), sliders, checks, BOM, and steps.
  • The Python DSL, with submodels built once and placed many times, .mpd output, and a three.js render that updates live from the project folder.
  • Versions: save one any time, an automatic one before every agent turn, and restore or open any of them as a new project, so iterating is never risky.
  • Parts search, and a BOM with Rebrickable colors and availability.
  • Validator v1 (collision, connectivity, floating parts, step order, availability), with findings fed to the agent as tool output and linked to the viewer and to source lines.
  • Sliders from the params declared in model.py, plus a "make this the default" action.
  • Photo input: image attachments to both agents, a compare view, and the reference-photo doctrine (4D).
  • Native PDF instructions: step pages, parts callouts, cover and BOM pages, A4 and Letter (4E).
  • A technique library mined from official models: at least 30 accepted techniques with tests and provenance (3C).
  • Exit: rungs 1–3 and the photo rung pass the live eval on both agents; the rung 2 PDF prints legibly at A4 and Letter; the mined techniques are in and rung 2 scores didn't regress; the integration and E2E suites are green on both OSes; the performance budgets in section 13 hold; the security review in section 15 is done; and Barry has done a hands-on pass on the Windows VM. While D-43 holds, "both OSes" and the Windows pass are macOS only; the Windows CI jobs and the Windows pass come back in one pass once the Mac app works.

Non-goals

No hosting, accounts, or telemetry. No Linux, mobile, or WebGPU. Emmet never calls an LLM API itself: all model use goes through the user's own agent CLI. Owned-inventory matching, BrickLink pricing, third-party MCP hosting, Studio .io files are deferred to Phase 8.

Eight design laws

  1. The viewer is sacred. It never moves the camera on its own, never blocks, and always shows the last good model while a new one builds.
  2. Every finding is one click from its parts. Clicking a check highlights the parts in the viewer and says what's wrong in a plain sentence. The model.py line that placed them goes to the agent, never to the screen: the user can't fix Python, so the app never shows code or offers to open a code file.
  3. The user always knows what the agent is doing. Every tool call is a visible card with a one-line plain-language summary.
  4. Real parts, real colors. Anything that can't be bought in that color is flagged, never hidden.
  5. Files are the truth. Anything the app shows can be reproduced from the project folder with emmet run and emmet check.
  6. Words before knobs. Parameters are named in the user's words and explain themselves on hover.
  7. The loop is fast. A slider change shows up in the viewer in under 1.5 s on rung 2.
  8. The user can always step in. The agent asks with a question card when a choice is the user's, a message typed mid-turn redirects it at its next step, and Stop is always one key away.

04System architecture

Flows

Prompt

The user types in the chat pane. The host sends the turn to the agent session. The agent calls search_parts, edits model.py, and calls run_model and then validate, getting findings back as tool output. It calls render to look at the result, fixes what it sees, and replies. The agent builds in stages and runs after each one, so the viewer grows live throughout, with new parts dropping in brick by brick.

Slider

The UI writes params.json atomically. The watcher triggers emmet run and then emmet check (latest wins, and a stale run is canceled). The viewer diffs the placement list by Emmet id and updates only what moved. No agent is involved and no tokens are spent.

Finding click

The Checks tab lists findings from build/validation.json. Clicking one highlights its parts and shows model.py:42. "Ask the agent to fix" sends the finding as a structured message to the current session.

Terminal power user

The user runs their own agent in a terminal inside a project folder. The project's AGENTS.md and CLAUDE.md point it at emmet and emmet mcp. The app, if open, watches the folder and renders, and highlight reaches it over the socket. Without the app, render falls back to the headless render mode.

Question

The agent calls emmet_host.ask_user. emmet_host forwards the question over the bus, the chat shows a question card, which says it waits on you. The user clicks an option or types Other, and the answer goes back as the tool result, so the agent carries on in the same turn.

Redirect and stop

The user types while the agent works. The message waits as a pending bubble and is delivered at the agent's next step: native mid-turn input if the CLI has it, otherwise attached to the next emmet tool result through the bus. Stop interrupts the turn at once, and a still-pending message goes out as the next turn.

Rules

  1. Sources: model.py, models/*.py, params.json, emmet.toml, and CARD.md. Derived: everything in build/. emmet run && emmet check on a clean checkout reproduces build/ byte for byte, given the same Emmet, library, and parts data versions, except the run-only fields that describe a run rather than the model: the timings and generation counter (kept in manifest.json's run block), run.log, and renders/. The comparison leaves those out, and an integration test proves the rest.
  2. Who writes what. The agent edits model.py, models/, and CARD.md. The UI writes params.json and emmet.toml, plus model.py only through emmet params --write-default, a single-literal AST rewrite. Only emmet writes build/ and history/.
  3. Atomic writes everywhere: write to *.tmp in the same directory, fsync, rename. Readers never see half a file.
  4. Staleness is visible. manifest.json carries inputs_hash = sha256 of the sources, the params, the Emmet version, the library version, and the parts data pack version (availability findings depend on it). If the hash doesn't match the current inputs, the UI shows "out of date: rebuilding" and keeps the last good model on screen.
  5. Generation counter. Each run increments generation. The viewer ignores events older than what it shows, and the run queue cancels superseded runs.
  6. Watcher. It watches sources only (not build/), debounced 150 ms, and ignores editor temp files.
  7. Versions (Barry 2026-10-27). A version is a copy of the sources (model.py, models/, params.json, emmet.toml, CARD.md) plus that build's model.mpd and placements.json (so a version shows without running it) and a thumbnail render, in history/<n>-<slug>/ with a version.json (name, note, time, who made it, part count, inputs_hash). The user saves one any time ("Save version", ⌘S) and keeps iterating without fear. Emmet saves one automatically before every agent turn that changes the sources, so any turn can be undone; the last 20 automatic versions are kept, and named versions until the user deletes them. Restoring first saves the current state as a version, then writes the sources back atomically, so a restore is never a loss. "Open as a new project" copies a version out to try a different direction side by side.
  8. Imports. Opening a bare .ldr or .mpd creates a project whose model.py is import_ldraw("source.mpd"). The agent can then refactor it into a parametric model.
  9. Schema version. emmet.toml has schema = 1. A newer app migrates forward explicitly and never silently.

08The model DSL (emmet_dsl)

The DSL is the agent's language, so it's designed for agents first: grid units instead of LDraw units, footprint placement instead of part origins, stable ids, and errors that name the line. docs/spec/dsl.md is the full reference, and emmet api prints it from the docstrings.

Frame and units

  • Z is up. x runs right and y runs back, both in studs (1 stud = 20 LDU). z counts plates (1 plate = 8 LDU, 1 brick = 3 plates = 24 LDU). The DSL converts to LDraw's −Y-up LDU frame on output: the DSL point (x, y, z) is the LDraw point (20·y, −8·z, −20·x), a proper rotation, so rot stays a rotation. A fixture test pins the signs against a hand-checked .ldr.
  • Footprint placement. at=(x, y, z) is the minimum corner of the part's body footprint, studs excluded, after rotation. A 2×4 brick at (0, 0, 0) with rot=0 covers x 0–2, y 0–4, z 0–3. Offsets come from the part's body box in the index. A baseplate is half a plate thick, so a model on one starts at z = 0.5.
  • Rotation. rot is a quarter-turn count about Z (0–3) by default. rot=Rot(x=90, z=45) handles anything else, and add_raw(part, color, matrix_ldu) is the escape hatch.
  • Parts are referenced by LDraw id ("3001") or by a helper (Brick(2, 4), Plate(1, 6), Tile(2, 2), Slope(45, 2, 1)). Helpers resolve through the index and fail loudly with suggestions.
  • Colors are referenced by name (LDraw, Rebrickable, or BrickLink spelling; "Light Bluish Gray" and "LBG" both work) or by LDraw code.

Example

from typing import Annotated
from emmet_dsl import model, Model, Range, Color, Brick, Plate, Slope

@model
def cottage(
    width: Annotated[int, Range(6, 16)] = 8,
    depth: Annotated[int, Range(4, 12)] = 6,
    wall_rows: Annotated[int, Range(3, 8)] = 5,
    wall_color: Color = "Tan",
    roof_color: Color = "Dark Red",
    chimney: bool = True,
):
    """A small cottage on a green baseplate.

    width: how many studs wide the house is
    depth: how many studs deep the house is
    wall_rows: how many bricks tall the walls are
    chimney: add a brick chimney on the roof
    """
    m = Model()
    with m.step("Baseplate"):
        m.add("3811", "Green", at=(0, 0, 0), id="base")
    for row in range(wall_rows):
        for side in ("back", "sides", "front"):    # a wall a step, the far side first
            with m.step(f"Walls, row {row + 1}: {side}"):
                m.wall(x=2, y=2, z=0.5 + 3 * row, length=width, depth=depth, sides=side,
                       color=wall_color, bond="running", openings=door_and_windows(width, row))
        if row == 1:                                # the room, while the walls are low
            with m.step("Inside: table and bed"):
                furnish(m, width, depth)
    with m.step("Roof"):                            # a technique brings its own steps
        m.use("gable_roof", x=2, y=2, z=0.5 + 3 * wall_rows, width=width, depth=depth, color=roof_color)
    if chimney:
        with m.step("Chimney"):
            m.stack(Brick(1, 2), "Reddish Brown", at=(width - 1, depth // 2, 0.5 + 3 * wall_rows), count=4)
    return m

API surface (v1, finished in 3B)

CallDoes

Build steps, like an instruction book

Steps are what a person builds from, on screen (section 13) and in the PDF (4E), so they break the build down the way official instruction books do (Barry 2026-10-27, from the books he builds from). The doctrine teaches it, the validator checks what it can (step_order, step_size), and the templates show it: the cottage builds its walls a wall at a time, furnishes the room at the second row, and raises the chimney with the walls.

  • Bottom up, a layer at a time. Walls rise a row at a time, and each row goes on a wall at a time, the far side first, so each step's new parts are in view. A model made of sections (a wall panel, a floor, a tower) builds one section at a time.
  • Small steps. A step adds a few parts: about 2 to 8 for a 6+ build, 1 to 4 for 4+, and up to about 12 for 18+ when they're the same part in a plain run. A bigger step is split by wall, side, or row. The Age build setting sets the target.
  • The inside goes in while it's easy to reach. Furniture and interior details go in while the walls are low, or with one side left open (a wall built as a section and closed after). Never after a ceiling or roof has closed the room in.
  • Features go up with the structure. A chimney, a column, or a drainpipe gains a piece in each layer's step, not one tall stack at the end. Adding a feature means putting its parts in the steps where a builder would add them, and reordering when the old order no longer works; never a step tacked onto the end. The agent checks the order again after every change.
  • Sub-assemblies. A unit built apart and then attached (a door in its frame, a window with its glass, a tree, a bookcase) is a submodel with its own steps, numbered 1, 2, 3 inside its box. A unit built more than once is built once and marked "2x". Parts the model adds outside any step get steps a layer at a time, bottom up, at most the step target each (3B).
  • Titles group steps. A title reads "Walls, row 2: back wall": the part before the colon groups steps in the steps list. The PDF prints step numbers, not titles, like the books.

How a step is shown, on screen and in the PDF, laid out the same way:

  • The step number, large, at the top left, under the parts box: a picture of each new part in its color with its count ("2x"), larger parts first. No part numbers; the BOM page has them.
  • The model built up to the step: earlier parts at full color, the step's new parts outlined in red, later parts hidden.
  • A sub-assembly is drawn in a framed box with its own parts box and numbered sub-steps (1, 2, 3); the next picture shows it going on, with a line from the box to where it goes, and "2x" on the box when it's built twice.
  • Arrows show which way a part goes on when that isn't obvious; a zoom box shows a part placed somewhere hidden; a turn icon marks a step where the model turns around or over. The camera stays put through a run of steps and moves only when the model turns.

Ids, source lines, and output

Each placed part is written to the .mpd with a meta line before it, which other LDraw tools ignore:

0 !EMMET ID walls-row-3/12 SRC model.py:27
1 19 40 -72 60 1 0 0 0 1 0 0 0 1 3001.dat

Ids are stable across runs for the same inputs, which is what lets the viewer diff, the Checks tab link, and the agent say "move roof/4". The DSL raises EmmetError with a code (section 09) and the user's file and line, never a stack trace into emmet_dsl internals.

What the DSL is not

It's not a sandbox. model.py is ordinary Python, and the protection is workspace trust plus the subprocess limits in section 15. By convention, models do no file I/O outside the project and no network, and emmet rules says so.

10Agent bridge

Both agents are first-class from the spike (D-06). The bridge's job: start the user's own CLI with Emmet's tools and instructions, turn its protocol into one normalized event stream for the chat pane, and route permission requests to the user. All of this happens without touching the user's agent config (D-26).

The trait

pub trait AgentAdapter: Send + Sync {
    fn kind(&self) -> AgentKind;                          // Claude | Codex
    fn detect(&self) -> Detection;                        // path, version, supported?, signed_in?
    fn start(&self, cfg: SessionConfig) -> Result<Box<dyn Session>, AgentError>;
    fn usage(&self) -> Result<UsageSnapshot, AgentError>;            // billing state, plus plan meters where documented (D-36)
}
pub trait Session: Send {
    fn send(&mut self, turn: UserTurn) -> Result<(), AgentError>;    // text (+ structured context: selection, finding)
    fn respond(&mut self, id: ApprovalId, d: Decision) -> Result<(), AgentError>;
    fn interrupt(&mut self) -> Result<(), AgentError>;
    fn answer(&mut self, id: QuestionId, a: Answer) -> Result<(), AgentError>;   // a question card (1C)
    fn steer(&mut self, text: &str) -> Result<UserNote, AgentError>; // NoteDelivered says by which path
    fn cancel_note(&mut self, id: NoteId) -> bool;  fn edit_note(&mut self, id: NoteId, text: &str) -> bool; // until delivered
    fn events(&mut self) -> EventStream;                            // AgentEvent below
    fn resume_token(&self) -> Option<String>;                      // Claude session id / Codex thread id
    fn close(&mut self);
}
pub enum AgentEvent {
    Started { resume: String, model: Option<String>, billing: Option<Billing> },
    Text { message: String, delta: String }, Reasoning { message: String, delta: String },
    ToolCall { id: String, name: String, input: Value }, ToolResult { id: String, ok: bool, summary: String },
    FileChange { path: PathBuf, kind: ChangeKind },
    Approval { id: ApprovalId, kind: ApprovalKind, tool: String, detail: String }, ApprovalClosed { id: ApprovalId },
    Question { id: QuestionId, question: Question },                // from emmet_host.ask_user, via the bus
    QuestionClosed { id: QuestionId, reason: Option<String> },
    NoteDelivered { id: NoteId, path: SteerPath },
    Usage { input: u64, output: u64 }, TurnDone { reason: DoneReason },
    Models { models: Vec<ModelChoice> },                          // what the model and effort picker offers (4B)
    Limits { snapshot: UsageSnapshot },                              // live: Claude's rate_limit_event
    Error { code: AgentErrorCode, message: String },
    Exited { code: Option<i32> },                                 // the CLI ended; nothing follows
}

Questions, redirects, and stops

These three work the same on both agents, because they run through Emmet's own tools and bus, not through either CLI's UI.

  • Question cards (D-32). emmet mcp-host (the emmet_host server) turns an ask_user call into a bus request. The host emits a Question event, the chat shows the card, and the answer goes back as the tool result. One question is open per session at a time. Text typed in the composer while a question is open counts as its Other answer. Stop cancels the question (reason: "stopped"). If a CLI's tool timeout turns out to be capped below a usable wait, ask_user returns reason: "timeout" just before the cap, the doctrine has the agent end its turn, the card stays open, and the answer is sent as the next turn.
  • Redirect (D-33). A message sent while the agent works becomes a pending note, shown as a bubble that says "Delivered at the agent's next step", with Edit and Cancel. steer() picks the first path that applies: (1) native mid-turn input, where 0B shows the CLI supports it; (2) queued: the note waits on the bus until emmet mcp --session attaches it to the next emmet tool result as user_notes; (3) if the turn ends first, the note is sent as the next turn right away. When it's delivered, the bubble turns into a normal message with a "Delivered" mark. If nothing delivers it within 20 s, the bubble offers "Stop and send now".
  • Stop. Esc or the Stop button calls interrupt(). The turn ends, in-flight runs finish normally (writes are atomic, so the project stays consistent), and pending notes go out as the next turn, prefixed "(You stopped the previous turn.)".
  • Recording. Questions, answers, and notes are part of the transcript, so replay tests cover them like any other event.

11Validator and connections

This is the hardest part and the biggest differentiator. LDraw describes shapes, not how parts connect, so Emmet builds a connection model on top. The validator is judged by three numbers, all checked in CI.

Precision

Zero error-severity findings on the official-model corpus (OMR models are buildable by definition). Every false positive found is a bug with a test.

Recall

≥ 95 % of injected faults detected: a part shifted by a plate, a support removed, a part rotated, a collision added.

Speed

≤ 300 ms for 500 parts and ≤ 1.5 s for 2,000 on an M1, warm (collision proxies cached), and ≤ 3.5 s for 5,000 from 8I on. Incremental re-checks of changed parts come later if needed.

Connection data model

pub struct Connector {
    pub kind: ConnKind,        // Stud, AntiStud, StudHole (tube/bottom), Axle, AxleHole, Pin, PinHole, Bar, Clip, Hinge…
    pub pos: Vec3,             // part-local LDU
    pub dir: Vec3,             // unit normal pointing out of the part (studs point up = −Y in LDraw)
    pub gender: Gender,        // Male | Female
    pub radius: f32,           // for matching cylinders (stud 6 LDU, bar 4 LDU …)
    pub source: ConnSource,    // Primitive("stud.dat") | Shadow | Override
}
pub struct PartGeometry { id: PartId, body_box: Aabb, collision: CollisionProxy, connectors: Vec<Connector> }
pub struct Connection { a: (PlacedId, usize), b: (PlacedId, usize), kind: ConnKind }

As built in 3A (ADR 0013, docs/spec/validator.md): connectors follow LDCad's snap model (cylinders with sections, clips, fingers, generic plugs), are computed per run from the part files and cached in memory, and a file's connectors are its subfiles' plus its own. A pair seats within 0.5 LDU across the axis for studs and 1 LDU for round joints (D-45).

Connector sources, in order:

  1. Primitive scan (covers most System parts): a part's subfile references to stud primitives (stud.dat, stud2.dat, stud3.dat, stud4.dat, stud10.dat, the stu2* families, box5 tubes …) become connectors at their transformed positions. The mapping is a table in emmet-core with a test per primitive.
  2. LDCad shadow library (!LDCAD SNAP_* meta for clips, bars, pins, axles, hinges). It is CC BY-SA 4.0 (ADR 0003), so the connector data built from it ships as its own data file under CC BY-SA 4.0, with attribution to the LDCad Shadow Library, separate from the AGPL code (Barry 2026-10-24, Q-01), compiled into the binary unchanged (D-44). It covers 94 of ldraw-mini's 141 real parts; track and the 9V switch need overrides.
  3. Overrides in data/connections/*.toml for anything wrong or missing, each with a test model. An override can add to a part's connectors or replace them.

API (packages/viewer)

How it renders

  • Unique parts once. LDrawLoader loads each unique part (through the emmet-lib:// custom protocol, which serves library files from app data with an in-memory cache) and produces geometry with LDraw edge lines and conditional lines. Geometry is cached by part id.
  • Instancing. One InstancedMesh per (part, color). Highlight and selection use per-instance color attributes, not material swaps. A 2,000-part model stays under ~300 draw calls.
  • Materials follow the LDraw color table: solid, transparent (sorted, depth-write off), chrome and metal (environment map), rubber, and glow. There's a soft studio light rig and an optional ground shadow.
  • Studs. High detail up close, with logo-less low-poly studs past a distance threshold (a quality setting).
  • Diff updates keep the camera, selection, and step state. The last good scene stays up while a run is in flight or failed.
  • Build animation (D-34). Runs started by the agent update with animate: "build", so you watch the model go together:
    • Order: build step, then bottom-up by layer, then nearest to the previous part, so no part ever appears floating.
    • Motion: each added part drops from about three plates above and fades in over ~160 ms with ease-out. Removed parts lift and fade out (150 ms), and moved parts glide (200 ms).
    • Pace: Animated staggers parts ~30 ms apart and caps the batch at 6 s, however many parts arrive. Fast fits the batch into 0.6 s, and Off applies it at once. Reduced motion forces Off.
    • Never in the way: slider runs use animate: "none" (law 7). A new run finishes the current animation instantly before applying its own diff. The Skip button and any click in the viewer jump to the end, and orbiting doesn't interrupt it. The camera never moves (law 1).
    • Replay build in the viewer toolbar plays the whole model from empty. It's a good way to review a finished model and to demo.
    • Renders for the agent always show the final state, never a frame mid-animation.
    • Only animating instances get per-frame matrix updates. Everything else stays static in its InstancedMesh.
  • Steps show the build up to the step chosen in the steps list, the way section 08's step rules lay it out: earlier steps at full color, the step's new parts outlined in red, later steps hidden, and the step number with its parts box (and any sub-assembly box) over the top left of the viewer.
  • Render mode (D-24): Emmet --render <project> --view … --out … opens a hidden window, renders through the same viewer.render, writes the PNG, and exits. When the app is already running, render goes over the bus to the open window instead. ADR 0005 proves this on both webviews and records the fallback (an off-screen visible window) if a hidden WebGL context is throttled.

Rules that keep this fast

  • CI time budget: a PR's macOS job finishes in ≤ 10 minutes and the Windows job in ≤ 15. While D-43 holds, the Windows jobs run only in a manual run with its "windows" box checked (EMMET_CI_WINDOWS=1). A test that pushes past the budget moves to nightly or gets faster. Timings are printed in the job summary.
  • Run only what a change can break: scripts/ci-scope.sh picks the jobs from the changed paths (prose runs only the plan job; the UI and viewer skip Windows, which covers paths, processes, the sidecars, and Python), a push after a green run tests only its own commits, and a merge doesn't rerun on main.   • Fixtures stay small: ldraw-mini is ~200 parts, and replay files are under 200 KB each.
  • No mocks of our own code: fakes exist only at external boundaries (the agent CLIs, the network downloads).

# Emmet

Emmet is a Tauri 2 desktop app (macOS + Windows) where the user's own Claude Code or Codex agent builds brick
models from real LDraw parts by writing a parametric Python model (emmet_dsl). The plan is docs/plan.html; progress
is docs/plan-status.js. Section 19 of the plan has the agent rules; they apply to every task here.

## Commands
just setup · just dev · just check · just test [--changed] · just e2e · just ci (CI's mac job, scoped to the change)

## Map
crates/emmet-core (LDraw, index, validator, BOM, steps) · crates/emmet-agent (Claude/Codex adapters) ·
crates/emmet-bus (local socket) · crates/emmet-cli (emmet + emmet mcp) · apps/desktop (Tauri host + React UI) ·
packages/viewer (three.js) · python/emmet_dsl · tests/it (integration) · tests/e2e (WebdriverIO) · docs/

## Invariants
- Project files are the source of truth; build/ is derived and reproducible.
- Never write to ~/.claude, ~/.codex or any user-level agent config.
- Integration tests first; unit tests only for dense logic; test in proportion to real risk; never weaken a test to get green.
- No new dependency or tool without approval (plan section 19, rule 6).
- Every IPC path is checked against the project root; all process spawning is in Rust.
- No secrets, real names, emails or personal paths in the repo, fixtures, transcripts or screenshots. The exceptions:
  Barry's name where the license needs it (copyright lines, TRADEMARKS.md) and in commits and sign-offs, which use his
  GitHub noreply address; and third-party authors' names that a license requires us to keep (LDraw parts, OMR models,
  and their attribution files).
- PR titles: `<session id>: <outcome>` for a session ("0B: Research spikes and ADRs"), `<area>: <change>` otherwise
