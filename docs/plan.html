Emmet: build plan for an agent-driven brick CAD app

Emmet is a free desktop app for macOS and Windows that does for brick models what nurb does for CAD. You describe or change a model in plain words. Your own Claude Code or Codex agent builds it from real LDraw parts by writing a parametric Python model, and you watch it take shape in a polished 3D viewer with sliders, buildability checks, a parts list, and build steps. It's local only: no hosting, no accounts, and you bring your own agent.

Prepared 2026-10-24 for Barry Mortenson · Repo barrymortenson/emmet (private until launch) · This plan: docs/plan.html · Status: docs/plan-status.js · Marketing site later: emmetbuilder.com

How to use this document Sections 02–18 are the specification: what to build and why. Sections 19–22 are the execution plan: nine phases, each split into a few large sessions. A session is one agent run, one branch, and one pull request. Every session has a Copy prompt with rules button that puts the agent rules, the session's scope, its Done when list, and its prompt on the clipboard in one go, ready to paste into Claude Code or Codex. Steps marked YOU need you. The left rail reads docs/plan-status.js and shows what's done, what's in progress, what's up next, and what's waiting on you.

01Read me first

Fast start

  1. Do Phase 0's people steps (section 21): approve creating the private repo and register the self-hosted runner on this Mac. Claude Code 2.1.310 and Codex 0.160.1 are already installed here; just confirm both are signed in.
  2. Open the next session. The rail's Up next box names it and has a copy button. You can also press Copy prompt with rules on the session itself.
  3. Paste it into Claude Code or Codex, started in ~/Sites/emmet. The agent checks the prerequisites, builds, tests, updates docs/plan-status.js on its branch, opens one PR, and stops.
  4. Review and merge. The status change lands with the merge, so the rail is right on the next reload. Repeat.
  5. To let one agent run a whole phase, use that phase's Copy phase prompt button (section 19). It still stops at every merge unless you add merge permission for that run.

Which document wins

  • Section 03 (decisions of record) and accepted ADRs in docs/adr/ win over any other text in this plan. An ADR that changes a decision updates section 03 in the same PR.
  • The repo's AGENTS.md (with CLAUDE.md as a symlink) binds every session. If it conflicts with this plan, the agent stops and asks, and the loser gets corrected.
  • When the plan and the code disagree, the agent stops and asks. It never guesses which one is right.

Who it's for

  • Brick hobbyists who already pay for Claude or Codex and want to go from an idea to a buildable, real-parts model in minutes, then tune it with sliders instead of placing 400 parts by hand.
  • MOC builders who want parametric drafts (a station of any length, a house of any width) and an honest parts list.

Gaps Emmet owns

  1. A nurb-level UI and UX in a local desktop app for brick models.
  2. Live buildability validation fed back to the agent: collisions, connectivity, floating parts, weak overhangs, part and color availability, and buildable step order.
  3. Parametric models whose sliders drive regeneration.
  4. Later: a technique library (SNOT, hinges, jumper offsets) mined from official models.
  5. Later: build from owned inventory (Rebrickable) and BrickLink pricing.

MVP scope and exit criteria

The MVP is the end of Phase 5, the working proof of concept. Beta (Phase 6) and the website and launch (Phase 7) come after it.

  • A Tauri app on macOS and Windows: project tree, 3D viewer, chat pane wired to Claude Code and Codex, sliders, checks, BOM, and steps.
  • The Python DSL, .mpd output, and a three.js render that updates live from the project folder.
  • Parts search, and a BOM with Rebrickable colors and availability.
  • Validator v1 (collision, connectivity, floating parts, step order, availability), with findings fed to the agent as tool output and linked to the viewer and to source lines.
  • Sliders from the params declared in model.py, plus a "make this the default" action.
  • Exit: rungs 1–3 pass the live eval on both agents; the integration and E2E suites are green on both OSes; the performance budgets in section 13 hold; the security review in section 15 is done; and Barry has done a hands-on pass on the Windows VM.

Non-goals

No hosting, accounts, or telemetry. No Linux, mobile, or WebGPU. Emmet never calls an LLM API itself: all model use goes through the user's own agent CLI. Photo input, native PDF instructions, technique mining, owned-inventory matching, BrickLink pricing, and Studio .io files are deferred to Phase 8.

Seven design laws

  1. The viewer is sacred. It never moves the camera on its own, never blocks, and always shows the last good model while a new one builds.
  2. Every finding is one click from its part and its line. Clicking a check highlights the parts in the viewer and shows the model.py line that placed them.
  3. The user always knows what the agent is doing. Every tool call is a visible card with a one-line plain-language summary.
  4. Real parts, real colors. Anything that can't be bought in that color is flagged, never hidden.
  5. Files are the truth. Anything the app shows can be reproduced from the project folder with emmet run and emmet check.
  6. Words before knobs. Parameters are named in the user's words and explain themselves on hover.
  7. The loop is fast. A slider change shows up in the viewer in under 1.5 s on rung 2.

Flows

Prompt

The user types in the chat pane. The host sends the turn to the agent session. The agent calls search_parts, edits model.py, and calls run_model and then validate, getting findings back as tool output. It calls render to look at the result, fixes what it sees, and replies. The watcher sees each save, and the viewer updates live throughout.

Slider

The UI writes params.json atomically. The watcher triggers emmet run and then emmet check (latest wins, and a stale run is canceled). The viewer diffs the placement list by Emmet id and updates only what moved. No agent is involved and no tokens are spent.

Finding click

The Checks drawer lists findings from build/validation.json. Clicking one highlights its parts and shows model.py:42. "Ask the agent to fix" sends the finding as a structured message to the current session.

Terminal power user

The user runs their own agent in a terminal inside a project folder. The project's AGENTS.md and CLAUDE.md point it at emmet and emmet mcp. The app, if open, watches the folder and renders, and highlight reaches it over the socket. Without the app, render falls back to the headless render mode.

Trust boundaries

  • Webview → host. The UI has no filesystem, shell, or network access of its own. It calls typed commands that validate every path against the open project root.
  • Host → agent CLI. The CLI is the user's own, logged in with the user's account, and runs with Emmet's permission policy (section 10). Emmet never sees tokens.
  • Host → Python. model.py is code. It runs in a subprocess (python -I, scrubbed env, project cwd, timeout, output size cap), only for trusted projects (D-27).
  • Network. Emmet itself downloads only the LDraw library, the Rebrickable CSVs, the uv-managed Python, and updates, all over HTTPS with pinned checksums where the source allows. The agent CLIs make their own traffic.

Rules

  1. Sources: model.py, models/*.py, params.json, emmet.toml, and CARD.md. Derived: everything in build/. emmet run && emmet check on a clean checkout reproduces build/ byte for byte, given the same Emmet and library versions. An integration test proves it.
  2. Who writes what. The agent edits model.py, models/, and CARD.md. The UI writes params.json and emmet.toml, plus model.py only through emmet params --write-default, a single-literal AST rewrite. Only emmet writes build/.
  3. Atomic writes everywhere: write to *.tmp in the same directory, fsync, rename. Readers never see half a file.
  4. Staleness is visible. manifest.json carries inputs_hash = sha256 of the sources, the params, the Emmet version, and the library version. If the hash doesn't match the current inputs, the UI shows "out of date: rebuilding" and keeps the last good model on screen.
  5. Generation counter. Each run increments generation. The viewer ignores events older than what it shows, and the run queue cancels superseded runs.
  6. Watcher. It watches sources only (not build/), debounced 150 ms, and ignores editor temp files.
  7. Imports. Opening a bare .ldr or .mpd creates a project whose model.py is import_ldraw("source.mpd"). The agent can then refactor it into a parametric model.
  8. Schema version. emmet.toml has schema = 1. A newer app migrates forward explicitly and never silently.

08The model DSL (emmet_dsl)

The DSL is the agent's language, so it's designed for agents first: grid units instead of LDraw units, footprint placement instead of part origins, stable ids, and errors that name the line. docs/spec/dsl.md is the full reference, and emmet api prints it from the docstrings.

Frame and units

  • Z is up. x runs right and y runs back, both in studs (1 stud = 20 LDU). z counts plates (1 plate = 8 LDU, 1 brick = 3 plates = 24 LDU). The DSL converts to LDraw's −Y-up LDU frame on output, and a fixture test pins the signs.
  • Footprint placement. at=(x, y, z) is the minimum corner of the part's body footprint, studs excluded, after rotation. A 2×4 brick at (0, 0, 0) with rot=0 covers x 0–2, y 0–4, z 0–3. Offsets come from the part's body box in the index.
  • Rotation. rot is a quarter-turn count about Z (0–3) by default. rot=Rot(x=90, z=45) handles anything else, and add_raw(part, color, matrix_ldu) is the escape hatch.
  • Parts are referenced by LDraw id ("3001") or by a helper (Brick(2, 4), Plate(1, 6), Tile(2, 2), Slope(45, 2, 1)). Helpers resolve through the index and fail loudly with suggestions.
  • Colors are referenced by name (LDraw, Rebrickable, or BrickLink spelling; "Light Bluish Gray" and "LBG" both work) or by LDraw code.

Example

from typing import Annotated
from emmet_dsl import model, Model, Range, Color, Brick, Plate, Slope

@model
def cottage(
    width: Annotated[int, Range(6, 16)] = 8,
    depth: Annotated[int, Range(4, 12)] = 6,
    wall_rows: Annotated[int, Range(3, 8)] = 5,
    wall_color: Color = "Tan",
    roof_color: Color = "Dark Red",
    chimney: bool = True,
):
    """A small cottage on a green baseplate.

    width: how many studs wide the house is
    depth: how many studs deep the house is
    wall_rows: how many bricks tall the walls are
    chimney: add a brick chimney on the roof
    """
    m = Model()
    with m.step("Baseplate"):
        m.add("3811", "Green", at=(0, 0, 0), id="base")
    for row in range(wall_rows):
        with m.step(f"Walls, row {row + 1}"):
            m.wall(x=2, y=2, z=1 + 3 * row, length=width, depth=depth,
                   color=wall_color, bond="running", openings=door_and_windows(width, row))
    with m.step("Roof"):
        m.use("gable_roof", x=2, y=2, z=1 + 3 * wall_rows, width=width, depth=depth, color=roof_color)
    if chimney:
        with m.step("Chimney"):
            m.stack(Brick(1, 2), "Reddish Brown", at=(width - 1, depth // 2, 1 + 3 * wall_rows), count=4)
    return m

Ids, source lines, and output

Each placed part is written to the .mpd with a meta line before it, which other LDraw tools ignore:

0 !EMMET ID walls-row-3/12 SRC model.py:27
1 19 40 -72 60 1 0 0 0 1 0 0 0 1 3001.dat

Ids are stable across runs for the same inputs, which is what lets the viewer diff, the Checks drawer link, and the agent say "move roof/4". The DSL raises EmmetError with a code (section 09) and the user's file and line, never a stack trace into emmet_dsl internals.

What the DSL is not

It's not a sandbox. model.py is ordinary Python, and the protection is workspace trust plus the subprocess limits in section 15. By convention, models do no file I/O outside the project and no network, and emmet rules says so.

11Validator and connections

This is the hardest part and the biggest differentiator. LDraw describes shapes, not how parts connect, so Emmet builds a connection model on top. The validator is judged by three numbers, all checked in CI.

Precision

Zero error-severity findings on the official-model corpus (OMR models are buildable by definition). Every false positive found is a bug with a test.

Recall

≥ 95 % of injected faults detected: a part shifted by a plate, a support removed, a part rotated, a collision added.

Speed

≤ 300 ms for 500 parts and ≤ 1.5 s for 2,000 on an M1, warm. Incremental re-checks of changed parts come later if needed.

12Parts, colors and availability data

LDraw library

  • First run downloads the official complete library (complete.zip from library.ldraw.org) at the release pinned by this Emmet version, checks its sha256, and unzips it into app data (~/Library/Application Support/com.emmetbuilder.emmet/ldraw/, %APPDATA%\com.emmetbuilder.emmet\ldraw\). It shows a progress bar and is resumable. The unzip refuses entries that escape the target (zip-slip).
  • emmet library update moves to a newer pinned release that a later Emmet version ships. Projects record the release they last ran against, and the UI notes when a project was built on an older library.
  • The release workflow builds and ships the parts index (parts.sqlite) for the pinned library, so first run doesn't spend a minute indexing. A local rebuild is emmet library verify --reindex.
  • License. The library is CC BY 4.0, with some older parts still CC BY 2.0. Both require attribution. The About screen, NOTICE, and the site credit LDraw.org and the part authors. Emmet doesn't modify or redistribute part files except in the ldraw-mini test fixture, which keeps every header and ships an ATTRIBUTION.md.
  • Path handling. Subfile references are case-insensitive with mixed \ and /. Index keys are lowercased, separators normalized, and PathBuf is used everywhere. Windows tests cover this.

How it renders

  • Unique parts once. LDrawLoader loads each unique part (through the emmet-lib:// custom protocol, which serves library files from app data with an in-memory cache) and produces geometry with LDraw edge lines and conditional lines. Geometry is cached by part id.
  • Instancing. One InstancedMesh per (part, color). Highlight and selection use per-instance color attributes, not material swaps. A 2,000-part model stays under ~300 draw calls.
  • Materials follow the LDraw color table: solid, transparent (sorted, depth-write off), chrome and metal (environment map), rubber, and glow. There's a soft studio light rig and an optional ground shadow.
  • Studs. High detail up close, with logo-less low-poly studs past a distance threshold (a quality setting).
  • Diff updates keep the camera, selection, and step state. The last good scene stays up while a run is in flight or failed.
  • Steps show earlier steps dimmed and the current step at full color, with a scrubber.
  • Render mode (D-24): Emmet --render <project> --view … --out … opens a hidden window, renders through the same viewer.render, writes the PNG, and exits. When the app is already running, render goes over the bus to the open window instead. ADR 0005 proves this on both webviews and records the fallback (an off-screen visible window) if a hidden WebGL context is throttled.

Each session is large and coherent on purpose: one prompt carries a whole slice (the engine skeleton, the agent bridge, the validator), so you're running about twenty sessions, not hundreds of tasks. Sizes are rough agent effort: M is about a day, L two to three, XL up to a week.

  3. Weeks 1–3: the spike, 1A → 1B → 1C → 1D. Set up the Windows VM (H-04) and the signing identity (H-05) along the way. End with the 60-second demo and the G1 decision.
  4. Critical path to the proof of concept: 0A → 0B → 1A → 1B → 1C → 1D → (G1) → 3A ∥ 3B → 4A → 4B ∥ 4C → 5A ∥ 5B → (G2). Design (2A → 2B) runs alongside 1D and Phase 3.

1A Engine walking skeletonafter 0B · size L

Goal: From a terminal, emmet new → emmet run turns a Python cottage into a correct LDraw .mpd from the real library, parts search works, and an agent can do the same through emmet mcp. Every path is covered by integration tests on both OSes.

What gets built

  • Library manager: download the pinned complete.zip, sha256, resumable, zip-slip guard, install into app data (--data-dir / EMMET_DATA_DIR override; dev uses .dev-data/). emmet library status|install|verify.
  • Parts index: SQLite FTS5 schema per section 12 (parts, parts_fts, colors; connectors and elements can be empty for now), the dimension parser, synonyms, ranking, emmet search, emmet part, emmet colors.
  • emmet_dsl v0: @model, Model.add, step, the param schema from the signature (Annotated + Range, docstring help), the Z-up stud and plate frame with footprint placement (section 08), ids plus file:line, color names, EmmetError codes, and emitting build/model.mpd, placements.json, and manifest.json through python -I -m emmet_dsl.run. Footprint offsets come from a JSON part-geometry file that emmet run writes for the parts the model asks for (the DSL never reads the library itself).
  • Python bootstrap: a uv sidecar (dev: the uv on PATH) installs Python 3.13 and the emmet_dsl wheel into the app-data venv on first use. The subprocess limits in section 15 apply. emmet doctor [--fix].
  • emmet CLI: new (cottage template, CARD.md, AGENTS.md/CLAUDE.md, trust marker), run, params (get/set), search, part, colors, library, doctor, trust. The JSON envelope, error codes, exit codes, atomic writes, inputs_hash, and generation.
  • emmet mcp (rmcp, stdio): search_parts, part_info, run_model, get_params, set_params, list_colors. Schemas are exported to docs/spec/mcp/ with a CI freshness check.
  • Tests (tests/it): goldens for new → run → mpd/placements; the reproducibility check; broken models (syntax error, NameError, unknown part, unknown color, bad param, timeout, too large), each with the exact error envelope; 30+ golden search queries; an MCP contract test per tool; Windows path cases; library install against a local fixture zip (checksum mismatch, zip-slip entry, interrupted download).
  • docs/spec/dsl.md (v0) and docs/spec/project-format.md.
